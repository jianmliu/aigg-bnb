# Base-resident, on-demand family hosting

Approved user direction: host a base model family, keep the base resident for eligibility claims, and automatically execute tasks for future registered descendants. Child MEP, payment asset, royalty terms and execution dispute commitments remain exact-child identities. No sampled-claim protocol change or live contract migration.

Family mode is opt-in only for a registry with base enrollment enabled. Host UI lists root enrollment pools instead of hundreds of children; selecting a child for hosting redirects to its enrollment base. Legacy deployments keep the existing per-MEP path.

The base node keeps validated bytes/residency proofs. A family inbox handler accepts task/batch announcements for unknown future children without subscriptions per child. Before any model fetch or allocation, the page independently reads the configured chain market and registry: task exists, unsettled, not already submitted, assigned executor includes the bonded instance, task MEP/steps/stride/seed/init root/batch count match announcement, base routing belongs to a locally hosted pool. Read at a consistent block and bind to immutable running node identity. Network errors fail closed. Requests outside the hosted families or with false assignment do not fetch data.

Fetch a bounded FLYDELTAv3 in-place recipe from the child's on-chain DA and mirrors. Resolve ancestor recipes by content hashes using sibling content-addressed files and configured mirrors; verify every ancestor hash, family/layout and bound depth/count/bytes. Missing ancestry yields explicit refusal, never a fabricated parent. Recompute model/profile/base/royalty MEP exactly before execution; invalid DA or wrong model is not signed.

Use one bounded ephemeral execution node at a time, separate from base claim memory, so many future descendants cannot monotonically exhaust wasm. Persist a bounded replay journal (exact task, metadata, recipes, signed result) before delivering a signature. Retain replay records across reload; storage failure/backpressure refuses rather than deleting open obligations. Expose replay operation that reconstructs task commitments from base+recipes and verifies same result. Automatic on-chain dispute response is not added by this work. Base-only claims continue during descendant service; no child-specific bond or claim.

Bound downloads, request validation concurrency, replay cache and task deduplication. Error paths clean up child execution memory and allow later valid tasks. Existing single-model service remains compatible; family service prevents duplicate response from loaded child handlers. Browser UI shows family status and on-demand task activity, with capacity fixed to one execution slot.

Validation: start with only base, register child after host startup, assign real native/token-compatible task, fetch only recipe, validate and execute/result submit; second descendant without base refetch; bad task/unselected host/wrong base/wrong hash/missing ancestry/oversized recipe rejected; same task replay coalesced; claims still work; ancestry graph bound; journal failure prevents signing delivery; replay matches execution; legacy tests.
