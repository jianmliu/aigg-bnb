# Locked task and candidate pool before VRF assignment

Status: implemented and locally verified following the user's explicit selection of this approach. No live deployment is implied by local verification; a funded Chainlink VRF subscription and a new immutable market deployment are required.

## Objective and threat model

Eliminate free offline nonce grinding against a public epoch beacon for synchronous task assignment. Lock the task, execution fee, nonrefundable admission cost, and complete admitted-ready candidate snapshot before requesting unknown VRF output. Future stake, readiness, token preferences, candidate order, transaction ordering and fulfillment timing must not change the selected pair. This does not eliminate Sybil stake concentration, paying for many independent tasks, collusion, oracle withholding, or chain reorganization. Two matching outputs remain replication evidence, not a validity proof.

## Architecture

Preserve SynchronousTaskMarket v1 and its tests as the compatibility baseline. Extract small virtual admission/expiry/release hooks where necessary; a new VrfSynchronousTaskMarket replaces the legacy draw. A separate immutable-bound VrfAdmission controller performs bounded candidate snapshotting, leases, VRF request/fulfillment storage and deterministic weighted selection. A production adapter implements the official Chainlink VRF v2.5 subscription request/fulfillment ABI with authenticated immutable coordinator. Mock coordinators are tests only. No mutable coordinator, owner seed setter, reroll, user cancellation or fallback to the old beacon. Runtime code must fit EIP-170 and each transaction must remain within BSC's 16,777,216 gas cap.

## Lifecycle

1. Existing native/token single/batch posting APIs lock exact task inputs and client nonce; allowing a nonce is safe only because unknown VRF follows irreversible registration. The same task id cannot be reused. Execution fee and a separately quoted positive admission fee (same asset) are pulled atomically; admission cost is credited to an immutable recipient and never included in execution refunds. Admission policy cannot change an existing request.
2. Maintain a bounded global opt-in ready roster (initially 32 seats). Existing readiness APIs arm a seat only for positive-weight, non-exiting hosts with configured capacity; full live roster rejects only the new arm, never posting. Each arm expires after immutable READY_TTL blocks; signed readiness expiry remains the transaction authorization expiry, separate from readyUntil. Expired/inactive seats are permissionlessly prunable and reused. Do not scan the append-only registry enrollment history: one-wei historical enrollments must not poison admission. Snapshot ALL qualified hosts in this admitted-ready roster with valid base membership/residency, available capacity and accepted payment token. The caller cannot provide or trim the candidate list. Iterate ready roster slot order, record effective capped stake and readiness signer, consume readiness, hold bonds and reserve one capacity slot for every included candidate until the fixed maximum session end. Do not reserve unrelated or ineligible hosts. The ready roster itself bounds candidates; never accept a caller-selected subset or truncate an overlarge historical enrollment list. Initial ready roster/candidate bound is 32, subject to measured worst-case gas. This is an initial throughput limit, not a permanent scalability claim.
3. At least two candidates are required. A new task enters AwaitingRandomness (numeric phase 6, preserving phases 0..5). Fixed admission deadline and maximum execution deadline are recorded at posting. Request exactly one random word once; bind request id to this task before accepting any callback. Reentrant, synchronous and duplicate coordinator responses cannot bypass ordering.
4. Coordinator-authenticated fulfillment stores the one word and fulfillment block only; no user payments, candidate loop or fragile application calls in the callback. Unknown, duplicate or late responses cannot alter terminal state, resurrect tasks or change the word.
5. Anyone may advance allocation, but cannot choose its seed, timing-dependent pool or selected pair. Draw two distinct hosts using domain-separated hashes of the word and immutable task/snapshot identity, weighted without replacement. Do not skip selected hosts based on new readiness/capacity/eligibility. Transfer/retain already reserved leases without checking mutable capacity again. Pin the selected inbox signers for task routing. Release every unselected candidate's hold and lease; readiness stays consumed so resumption requires an explicit rearm. No selected-host replacement on refusal.
6. Commit/reveal/dispute deadlines derive from the recorded fulfillment block plus a fixed activation allowance, not the caller's allocation block. All deadlines remain under the posting-time lease/delegation maximum. If allocation is delayed past its fixed deadline, permissionless closure releases holds and refunds execution fees; admission cost remains spent. Candidates must know both wait and execution upper bounds before opting in.
7. Before randomness, timeout can happen only strictly after the immutable deadline, provided no timely fulfillment exists. Timely fulfillment prevents the caller from discarding the seed through a race with timeout. Late callback is ignored and cannot revive the task. No automatic rerequest. Execution/adjudication then retain v1 rules: terminal tasks cannot be challenged, inconclusive refunds original asset, silence is not computational fraud.

## Host and service behavior

New explicit verification mode `synchronous-vrf-v1`, core protocolVersion 1 plus admissionVersion 2. Fail closed if config claims old synchronous mode for a VRF market or vice versa. `/deployment` exposes admission controller, deadlines, fee quote and phase capabilities. Hosts see waiting-for-randomness while reserved, may not claim safe-to-close, and retain authorized task evidence. Unselected hosts become safe only after finalized reservation release and consumed readiness. Executing hosts route by immutable per-task signer, not the mutable readiness signer. Signed readiness authorizations must cover the maximum VRF wait plus full execution window.

Gateway and battery wait through phase 6 without requesting a manifest. Permissionless allocation/expiry is driven with existing transaction queues and simulation/budget checks. A restart resumes the same request/task rather than reposting or rerequesting VRF. Gateway quotes/escrows execution plus admission fees and records admission expense separately from refundable execution fee. A durable signed posting transaction is stored before broadcasting; restart retransmits only those exact bytes. Existing failed-call user billing stays zero with the gateway payer explicitly reported, so VRF mode requires an explicit persistent lifetime admission spending budget independent of pruned call history. Battery budgets must include the new admission cost per permitted attempt, or reject a VRF market explicitly until its policy is adapted; no silent underfunded posting. Task clients must not substitute arbitrary candidate lists.

Frontend shows bounded VRF wait, fixed candidate lock, selected/unselected outcome, fees and nonrefundable admission cost. Preserve v1 mode and safe-close semantics. A disconnected wallet is not evidence of safe closure for a retained session.

## Economic and operational limits

Locking all eligible candidates for one request is intentionally simple and auditable, but reduces concurrency during VRF waiting. The global ready-seat bound and admission cost bound transaction gas and charge for draws; bonded Sybil occupancy can still exclude honest hosts across models, so this is not an anti-DoS guarantee. Finite readiness leases permit stale seat reclamation; a larger-scale epoch batch/checkpointed candidate design is future work. Attackers may still buy many independent draws or cause inconclusive outcomes; do not promise zero collusion or refund-based free retries. Scientific experiment IDs and publication policy remain a separate protection against cherry-picked repeated experiments.

VRF native subscription funding is independent of execution assets. Same-asset admission fees do not automatically convert USDC/FLYBNB into BNB. Operators must fund the subscription. Deployment uses documented BSC testnet Chainlink coordinator/keyHash and reads coordinator config; no mock addresses or invented subscription ids in live configuration. Preserve existing NFT/treasury/legacy claims; any new collection transition requires audit before activation.

## Required evidence

- RED/GREEN tests for unknown VRF at posting, no assignment before fulfillment, complete snapshot, weight/availability immutability, duplicate hosts, one request per task, callback auth/replay/order, late callback, timeout race, assignment delay, no redraw, token/native fee conservation, candidate release and gas/bytecode bounds.
- Services/browser tests for phase 6, fixed task signer, explicit rearm, signed remaining lifetime, restart, delayed/out-of-order VRF, unsupported modes and no public-beacon fallback.
- End-to-end Anvil task with realistic model bytes and mock coordinator delay, actual gateway and worker commit/reveal, terminal safe close and refund flows.
- Live VRF proof/callback requires real funded subscription, separate from mock E2E. Do not mark production deployed without this evidence.
