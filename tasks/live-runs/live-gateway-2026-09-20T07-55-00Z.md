# BSC testnet live run — the gateway, end to end, with two real hosts

The first time a request entered the mesh through the public API, was executed by two independent
hosts that did not know each other, and was paid — and then the first time an adopted individual
earned its owner a royalty. It is also the run that found why neither had ever worked: two bugs, one
of them introduced by the fix for the first, and neither reachable by any test that runs on anvil.

Passed: 4 of 6 calls settled with both executors paid and agreeing; 2 failed and are the subject of
the sections below (refunded both times, nothing billed). Every transaction receipt succeeded.

- Network: BSC testnet (97), read at block 132104026
- TaskMarket: `0x71120BcF8EFDcc6E4c0299e035676dB6d0d68F19`
- InstanceRegistry: `0x50b015f2a2a04E2D177343bE4bDB652AFf8100B1`
- MEP: `0x312dda12d308ba13796472e6ba444be4a94a5b04ce9e5ef3ada3649034443f8a` — FlyWire female (FAFB
  v783, min5), 139,255 neurons, 2,700,513 synapse records, `int-lif`
- Payload: fetched from Greenfield and verified against the MEP's `model_id` before use
  (28,123,136 bytes, `js/fetch_brain.mjs`)
- Hosts: `0x3b3156A3…DD19` and `0x966d94F5…06D2`, funded 0.01 tBNB each, bonded 0.005 each,
  1 vote each, enrolled for the MEP. Brain resident in 10.4 s on first load, 1.9 s on the second
- Gateway: `aigg-bnb-gateway-testnet.onrender.com`, fee wallet `0xf5cfcb35…b5a7`

## Why the first call failed

To announce a task the gateway needs each drawn executor's **session key**. `InstanceRegistry` maps
session → instance, so the reverse is a log scan, and the gateway scanned `fromBlock: 0n`. Anvil
answers that instantly; BSC testnet's public RPC refuses it. The receipt named it exactly:

    results: { 0x3b3156…: { error: "RPC Request failed … eth_getLogs …" },
               0x966d94…: { error: "RPC Request failed … eth_getLogs …" } }

The task was on-chain, the sortition was correct, both hosts were connected to the relay and idle.
Nothing was announced, and the market refunded at the timeout. **Every test passed, because every
test runs against anvil.** Fixed in jianmliu/aigg-bnb#53: the scan is bounded and runs newest first,
which is also the right order, with the window and lookback configurable and a hit cached until its
expiry. The regression test puts an RPC in front of anvil that refuses a span it considers too
wide, as a public one does — two clean failures on the old code, two passes on the new.

That cache is the second bug, below. It is worth saying plainly: the fix for one live failure caused
the next one, and both were invisible to a test suite that never leaves anvil.

## What went right that is worth recording

- **`epoch_cold` is not a failure.** The first call to the redeployed gateway returned
  `503 epoch_cold, retry_after: 30` — epoch 660514 had no beacon yet, the lazy beacon being mid-wake.
  Nothing was spent. Thirty seconds later the same call settled. Refusing to spend when capacity is
  not there is the designed behaviour and it behaved.
- **A late `counts` vector degrades correctly.** On task 3 one host's spike counts did not arrive
  inside `GATEWAY_COUNTS_WAIT_MS`; the other's did and hashed to the settled digest, so the readout
  was served and marked *verified*. The counts are a convenience; the authority is the settled digest.
- **The gateway's state survived its own redeploy** — the failed call was still readable by id
  afterwards, from the disk the Blueprint mounts.

## The royalty path, end to end

The calls above ran against a base MEP with `royalty_bps = 0`, so they moved no royalty. To test the
part the collection exists for, founder **#0 was adopted** — the first individual of the genesis set
ever minted, and irreversibly so: `genesisMinted[0]` is set for good and 99 remain.

Building the fly's brain is the step no contract can do: its `model_id` is the base with the
individual's delta applied, hashed. Locally, from the published genesis recipe (228 bytes) over the
verified 77 MB `min2` base, that took **2.8 s** — and the id it produced is the one the chain then
bound, to the bit.

| step | | |
|---|---|---|
| `mint(0, …)` | `0x2bc78c6a…` | 0.01 tBNB, token 1 to `0xFE560Af8…`, of which 0.005 became the adopter's own bond |
| `register(1, …)` | `0x6148a2f9…` | MEP registered **with terms**: beneficiary the collection, 1000 bps |
| mep id | `0x8ceaa292…` | the terms are inside the id; the bare profile is `0xc1574973…` |
| relayer | — | picked the fly up off the whitelist on its own, as `fly #1` |
| two hosts | — | base + delta resident in 8.1 s and 12.5 s; 2/2 eligible after one epoch |
| task | `0x26beefeb…` | settled in 18.6 s, both executors returning `0x68e0c2ff…` |

Then the money, every figure read back from the chain:

| | wei | |
|---|---|---|
| fee | 20,000,000,000,000 | what the caller paid |
| → `market.royalties(mepId)` | 2,000,000,000,000 | **10%** — `ROYALTY_BPS` |

The task was posted `0x538c1a10…` and settled `0xd160477e…`; the royalty was drawn out of the market
and split by `collection.settle(1)` — `0x9ac640dd…`, 93,008 gas — and paid by `withdraw()` —
`0x7d679d29…`, 28,776 gas.

`market.royalties` and `owed[owner]` are both zero afterwards. The base vendor's 200,000,000,000 is
credited and still waiting: it is that address's to withdraw, not anybody else's to push.

This is the 9% / 1% the docs page states, and it is now a measurement rather than a reading of the
source. One thing it cost: a second gateway bug, found the same way (below).

## Why the fly's first call failed too

Task `0x04055593…`, posted against the fly, drew both hosts and neither answered — the same symptom
as the morning's failure, a different cause. A host delegates a **fresh session key every time it
reconnects**, and these two had restarted; the delegation each had used before was still live,
because an expiry is days out. #53's cache answered from it, so the gateway announced into keys
nobody was listening on. Drawn, silent, unpaid, refunded — and it would have stayed that way for
~3.5 days, until the old delegations lapsed.

Fixed in jianmliu/aigg-bnb#56: the entry records the block it was taken at and every call re-reads
the few blocks since, so a newer delegation always wins. The regression test re-delegates a provider
mid-run and stops the service on its old key, exactly as a closed tab does. The royalty call above
ran on that fix.

## The browser cannot host a fly at all

Not a failure of this run — a thing this run made visible, and the reason the two hosts here are
headless Node processes rather than the page.

A MEP registered under terms has id `keccak(profileId, beneficiary, royaltyBps)`, and **the terms
are nowhere in the bytes**. `PorwNode` keys a resident model by the id its payload computes, so it
registers the fly under the bare id while the chain draws it under the other one; every announcement
then looks up a model the node is in fact holding and misses. The page's worker also compares the
two and silently declines to serve when they differ (`matches: false`), so nothing is even logged.
Separately, the page can only `prepare` a whole payload, and a fly is a base plus a delta.

So the collection's royalty premise — that adopted individuals are hosted and earn — rested on a
client that could not host them. The protocol side was fine: these hosts proved it.

**Fixed the same day**, and shown on this network. jianmliu/aigg-porw#33 gave the node `terms` at
load, jianmliu/aigg-bnb#58 taught the page to recognise a delta and apply it, and #59 stopped it
re-downloading the base for every individual. Then founder #0's delta was published to Greenfield —
**named by its own hash**, which is the `deltaHash` the collection already records for the token, so
the object's name is derivable from the chain and its bytes verify against it. Re-read from a
different storage provider than the one it was uploaded to, it hashes to the on-chain value and its
own header binds the right base.

A browser tab then hosted founder #0 with nothing standing in for anything:

    fly #1: a 228-byte delta over FlyWire female · the founders' base (≥ 2 synapses) — fetching the base…
    fly #1: 77.1 MB base downloaded, checking its model_id…
    fly #1: model_id 0xbd6fbedc8734… matches the MEP
    fly #1: resident on the node, serving audits and tasks
    released the 74 MB base the individuals were applied over
    fly #1 epoch 660728: claim announced (slot 39 ms)

Ten and a half seconds from a URL to a resident brain, one wallet signature in the whole flow, and
the residency claim answered in 39 ms. **The convention this settles**: `weightsDA` may point at a
delta, the delta's own header binds its base, and the object is named by the delta's hash. No new
field, nothing to agree separately, and it holds for a bred individual as well as an adopted one.

Founder #0 keeps the ad-hoc `weightsDA` it was registered with (`gnfd://…min2.bin#delta:0x…`) —
that field is fixed at registration — so its URL is typed in rather than auto-filled. The next
individual registered will not need that, and the string is tidied when the collection is next
redeployed.

## The one that hid behind three wrong answers

Redeploying the relayer for the M3 merge took the hosts' claims away. Not their connections — their
claims. A host that had been up for two hours logged `claim announced` for **six consecutive
epochs** while the relayer's aggregator counted zero and rejected zero. Its eligibility lapsed, it
stopped being drawn, and the first thing to notice was a gateway call spending the whole wake
timeout and returning `model_cold`.

Three explanations were built and two were wrong, which is worth recording because each looked
right at the time:

1. **"The host's relay connection died."** It had not: `RelayClient` reconnects and replays its
   subscriptions, and `publish` throws when no socket is open. A local reproduction *did* fail this
   way — loudly — which is what made the wrong answer convincing. The live failure was silent.
2. **"The aggregator is only built in the pass that rolls the epoch."** It is not; `rolled` is read
   from the chain, so every pass builds it.
3. **"A race between `/epoch` and the aggregation pass."** Disproved by a test written specifically
   to lose that race, which passes on the unfixed code. The speculative fix that went with it was
   dropped rather than shipped.

The actual cause was four lines away from all of that. Subscribers on a relay topic were invoked in
a bare loop, so **the first to throw stopped the message reaching any of the rest** — and aggregators
are one per *epoch* on the same brain's topic. An aggregator for another epoch threw while
considering the claim, and the aggregator it was *for* never saw it. In Node the exception then
escaped the ws callback and took the process with it.

    delivered: 1    claims: 0    rejected: 0

Three numbers that should not be able to occur together. What found it was a five-line probe: two
subscribers on one topic, the first one throwing, and a question about whether the second still ran.

Fixed in jianmliu/aigg-porw#35 (handlers isolated, a throw counted and logged) with
jianmliu/aigg-porw#34 beside it — a host now learns whether its claim was *delivered*, which stops
it believing a lie even when something downstream eats the message. Both were needed, but only #35
was the cause: #34 is a separate hardening, and it was presented here as the fix for an hour before
the evidence said otherwise.

**After the fix, on the same network:** eight consecutive epochs counted, and the proofs are there.

    counted: 660891 … 660898        proof 660896: included (posted)
    before:  six consecutive zeros   proof 660897: included (posted)

## What stopped the verification, and will stop an adopter

The tab could not be brought back, and the reason had nothing to do with any of the above:

    HTTP 406  <Error><Code>30004</Code><Message>bucket quota overflow</Message></Error>

`aigg-brains` has no paid read quota. A hundred individuals of the collection are a hundred deltas
over the **same** 77 MB base, so every host that starts pulls it again — and an afternoon of a
handful of hosts starting up exhausted the free allowance. The alternate storage provider was
unreachable, so there was no second source.

Two things follow, and only the second was fixed today. The bucket needs a paid quota, or the base
needs somewhere else to come from: one provider is a single point of failure for every host of the
collection. And the page used to say **nothing at all** about this — it sat on "loading" for ever,
because the fetch was unchecked and the error reached only a log line nobody could act on
(jianmliu/aigg-bnb#67 repeats what the provider said, and adds that waiting will not help).

## Limits — what this run does NOT show

- **No dispute.** Both executors agreed on every settled call; the bisection path was not entered on
  this chain.
- **One royalty, on one individual, from one call.** The split is exact and the path is closed, but
  nothing here exercises a transfer (which settles the outgoing owner first), a second owner, or a
  fly bred rather than adopted. The base vendor's 200,000,000,000 wei is still credited, unwithdrawn:
  that address has to claim it itself, and no test here shows it can.
- **Two brains, one stimulus set, 100 steps, redundancy 2.** Nothing here speaks to the battery's
  5,000-step runs, to the measured 9.4× spread across stimuli, or to more than two providers.
- **Neither host of the PAID calls was a browser.** Both were headless Node processes, for the
  reason in the section above. A tab did hold founder #0 afterwards and claimed residency for it,
  but no task was drawn to that tab, so what a browser has been shown to do is host and prove — not
  yet execute a task and be paid for it.
- The two hosts ran on one machine as separate processes with separate keys. They are independent in
  every sense the protocol checks, and in no sense it does not.
- **99 founders remain.** Founder #0 is spent, to the project's own wallet, for this test.

## Rebuilt from the sources, not from a mirror

Everything above that touches the brains starts from bytes somebody is already serving: Greenfield,
the Cloudflare mirror added later that day, a peer's tab. Each of those can stop. So the last check
of the day started from the public record instead: Zenodo 10676866 (CC-BY-4.0) and the FlyWire
annotations repository, downloaded fresh, and `flywire_export.py` from the submodule.

Both brains came back byte-for-byte:

| | bytes | sha256 | `model_id` | on chain |
|---|---|---|---|---|
| min5 | 28,123,136 | `fd246cc2…` | `0x9747cc81…` | `exists()` true, same `model_id` |
| min2 (the base) | 77,074,432 | `10a9e16f…` | `0x53a7b48e…` | `exists()` true, same `model_id` |

16.8 s and 14.0 s of CPU. The `mep_id`s the rebuilds produce — `0x312dda12…` and `0x79af9764…` —
are the ones `MEPRegistry` at `0xC779151b…` already holds, and `claimBinding` on each returns the
`model_id` the rebuild computed. Public inputs, a deterministic transform, the content address, and
the chain: all four agree, with nothing this project hosts in the path.

The point is not that FlyWire makes a good CDN. It is that the mirrors are conveniences. A brain no
one is serving is still recoverable by anyone holding the papers, and a brain served by someone
hostile is still checked against the same address.

What this does **not** cover: the 100 founders. Each is a 228-byte delta *on* min2, and a delta is
only as recoverable as the place it was published to — today, Greenfield, and nowhere else. The
base is now reproducible from first principles; the individuals are not.
